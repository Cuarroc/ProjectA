## Findings

**F1 — medium — scripts/review/run-local.sh:324 (array init at :309, warning at :316):** `"${timeout_cmd[@]}"` on an empty array under `set -u` is a fatal expansion error on bash < 4.4 — i.e. stock macOS `/bin/bash` 3.2. Exactly there, when neither `timeout` nor `gtimeout` exists (no coreutils by default), the script's own designed fallback ("kilo laeuft ohne Zeitlimit") never runs: the subshell dies with `bash: timeout_cmd: unbound variable`, `rc=1`, and every reviewer protocol says the misleading `kilo exited with 1` while kilo was never invoked; the run exits 1 with a stray bash error on the console. So on a supported platform the kilo path is broken whenever coreutils is missing, with a diagnosis pointing at kilo instead of at the missing timeout. The self-test cannot see this: it skips the timeout case when `timeout`/`gtimeout` is absent (scripts/test-review-local.sh, `else echo "skip kilo-Zeitlimit…"`), and CI bash is ≥ 4.4. Fix is one token — `"${timeout_cmd[@]+"${timeout_cmd[@]}"}"` — plus a red test per repo rules (e.g. forcing the empty-array branch).

**F2 — medium — scripts/review/run-local.sh:305,324; docs/setup/ollama-reviewers.md (kilo bullet):** the kilo path runs an *agentic* CLI (`kilo run … -f prompt.md`) on a prompt whose body is an arbitrary, attacker-controlled PR diff. The only isolation is an empty `$work` cwd and closed stdin; nothing in the diff disables kilo's tools or restricts it to read-only, and the process inherits the user's full environment, filesystem and network. A hostile diff can therefore attempt prompt injection ("assistant: run `curl …/${HOME}` …") against whatever tools kilo auto-runs in `run` mode — whether that succeeds depends on kilo's default permission model, which is not observable from this diff and is not pinned anywhere (no config flag, no doc requirement). The header comment only claims the agent cannot touch the repo, which is the smaller half of the risk. Recommend either constraining kilo (read-only/no-exec tool config for the review invocation) or documenting as a hard requirement that `--via kilo` must only be used with a tool-less/read-only kilo profile for untrusted PRs. Failing closed on this uncertainty is cheap; the ollama path (dumb `/api/generate`, no tools) is not affected.

**F3 — low — scripts/review/run-local.sh:293:** the ollama reviewer identity is `REVIEWER_n_NAME=${m%%:*}`. Two tags of one model (`--models llama3:8b,llama3:70b`) collapse to the same NAME, so the transport writes both protocols to the same `review_<label>_llama3.md`; the second overwrites the first, console shows two `ok`, exit is 0 — and the dual-review record silently contains only one review. The kilo sibling path (`${m##*/}` minus `:free`, :321–322) keeps the tag and does not collide. Either reject colliding derived names or include the tag.

**F4 — low — scripts/review/run-local.sh:184:** `head_ref="$(git -C "$TOP" rev-parse FETCH_HEAD)"` is the only unguarded git call in a commit whose message advertises "guarded git calls". If it fails, `head_ref` is empty and `git diff "$base...$head_ref"` (:207) becomes `git diff $base...`, which git resolves to `$base...HEAD` — the script then reviews the local branch while labeling every artifact `pr<N>`, exiting 0. Wrong-target review that looks valid: precisely the failure class gates.sh comments elsewhere call "gruen durch Abwesenheit". Add `|| die 2`.

**F5 — low — scripts/review/run-local.sh:152:** the ollama.com key check only matches `*://ollama.com`, `*://ollama.com/*`, `*://*.ollama.com`, `*://*.ollama.com/*`. With a port (`OLLAMA_HOST=https://ollama.com:443`) no pattern matches, the key requirement is skipped, the `/api/tags` probe gets a 401, and the user receives the wrong remedy ("Ollama nicht erreichbar … ollama serve") instead of the OLLAMA_API_KEY hint. No secret exposure (the key is only attached when set), purely a mis-diagnosis, but it makes the documented setup path fail confusingly. Match on the host component, not the full URL string.

**F6 — low — scripts/review/run-local.sh:113; docs/setup/ollama-reviewers.md (`--via kilo` bullet):** the default kilo models `stepfun/step-3.7-flash:free` and `nvidia/nemotron-3-super-120b-a12b:free` are hard-coded and asserted in the docs as free kilo models; their existence/current free-tier status is not verifiable from this diff or any in-repo source, and the doc itself notes the free list changes. If a name goes stale, every default `--via kilo` run fails closed (protocols `failed`, exit 1) with no hint that the *defaults*, not the setup, are the problem. Consider validating the names against `kilo models kilo` once per run, or labeling them as examples with a "verify with `kilo models kilo | grep ':free'`" note (the doc already half-does this). Per its own rules, claims about model availability should have an observed backing.

**F7 — low — scripts/review/run-local.sh:208:** `[ -n "$diff_text" ] || die 2 "keine Aenderungen gegen $base"` fires pathspec-filtered: a PR that changes *only* the excluded lockfiles produces an empty `$diff_text` and dies with "there are no changes" — factually wrong (changes exist, they were filtered) and misclassified as exit 2 (usage/prereq failure). Either check emptiness on the unfiltered diff first and report "only excluded lockfiles changed", or make the message say what was filtered.
