Root prepares one concrete sheet for the user before the first actual protected run, by MS-3 before MS-4. Until the user decides that sheet, the product Orchestrator executes nothing autonomously. Afterward, only individually listed actions within a valid authorization may run. A general label such as “stage 1 in the project” is insufficient.

### Transaction, effect and recovery sequence (A2, A3, A6)

1. Authenticate the entrypoint and bind request/project/actual target/action to current authority, revisions and expiry. Validate typed key/value and evidence; record accepted request plus `Requested` atomically, or return a bounded denial without a protected effect. Replay of the same content returns its receipt, never another start.
2. Under the Store writer/maintenance discipline (`BEGIN IMMEDIATE`), reserve scope/key in accepted-event FIFO order. Recheck owner, code class, current area policy, authorization and revision; append `Checked`/decision. A probation or unknown earlier effect keeps its reservation; later requests wait or reject with reason.
3. Resolve authoritative old value, inverse and baseline in that transaction. A database-local change, revision, projection, approval consumption and journal transition commit together. No model/network await under the writer lock; failure commits neither half. This is a required Core contract, not the current planning-audit pattern.
4. For external effects, commit `EffectIntent` first, then invoke the registered adapter with the same request/intent identity. Revalidate grant/revoke/stop immediately before execution. Reconcile a lost receipt against actual target/process/artifact evidence; append `Applied` only after observed application. Uncertain outcome blocks the key; no blind replay or false distributed exactly-once claim.
5. Self-application requires a measured baseline and metric/tolerance. Run 24 observed, unpaused hours; persist each observation. Missing evidence leaves a proposal or pauses an active trial. Not-Aus blocks effects, pauses trials and cancels model requests; restart does not count unobserved downtime as success.
6. Confirm only after admissible measurements; degradation/error invokes the typed inverse through the same authority boundary. Recheck applied revision and concrete matching backup; preserve concurrent user edits, stop on conflict/corrupt backup/unknown owner. Append `Confirmed`, `RolledBack` or an unresolved recovery result with independent receipt. Rollback is also an effect requiring applicable authority; stop forbids it until authorized release/revalidation.
7. Emit typed invalidations after commit via `event_names.rs`; durable event ID/schema/project/request/revision/causation supports cursor/snapshot reread and notification dedupe. UI, report and attention consumers reread authorized state; events do not start workers or confer approval. Changed candidates invalidate affected evidence and reviews before delivery; Root accepts independent receipts, never author prose.

Area modes remain off/propose/self-with-report. Money, rights, security (including customer privacy), deletion, releases and own-level are fixed protected classes in Rust even with a corrupt register. Installs, secret changes and disabling protection retain their concrete protected authorization under P2. A valid prior specific grant is preserved within scope; it is never inferred from text or generalized. The rights sheet, trusted channel implementation/acceptance/operation and concrete activation remain prerequisites; no autonomous product effect before the sheet decision. Trust counts derive from confirmed trials and never self-elevate.
